# Идемпотентность и распределённые блокировки в TransferBoss

Документ фиксирует опыт и обоснование архитектуры двухуровневой защиты от дубликатов в TransferService.

## Проблема: откуда берутся дубликаты

Когда клиент отправляет `POST /api/v1/transfers`, один и тот же запрос может прийти повторно. Ниже — реальные сценарии, сгруппированные по источнику повтора.

### Пользователь нажимает повторно (миллисекунды — секунды)

Самый очевидный случай. Пользователь нажал "Отправить", не увидел реакции (спиннер не появился, интернет медленный) и нажал ещё раз. Два идентичных POST-запроса уходят с разницей в 200-500мс. Фронтенд может блокировать кнопку, но это не гарантия — запрос можно послать через devtools, curl, или мобильный клиент без debounce.

### Потеря ответа при живом соединении (секунды)

Сервер обработал запрос, создал перевод, отправил 201 Created — но ответ потерялся на обратном пути. Причины: TCP reset на промежуточном прокси, CDN обрезал соединение по таймауту, мобильная сеть переключилась с Wi-Fi на LTE посреди ответа. Клиент видит "connection reset" и ретраит. С точки зрения сервера это второй запрос, но перевод уже создан.

### API-шлюз / Load Balancer ретрай (секунды)

Nginx, Envoy, AWS ALB, Kong — все умеют ретраить запросы при ошибках upstream. Типичная конфигурация: если backend не ответил за 5с или вернул 502/503 — переслать на другой инстанс. Проблема: первый инстанс мог успеть создать перевод до того, как шлюз решил, что он "не ответил". Теперь второй инстанс получает тот же запрос. Особенно опасно, потому что это происходит **прозрачно** — ни клиент, ни бэкенд не знают о ретрае.

```
Client -> [ALB] -> Instance A (создал перевод, но ответ шёл 5.1с)
                   ALB решил: "таймаут" -> retry
           [ALB] -> Instance B (получает тот же запрос)
```

### Мобильное приложение: фон и восстановление (секунды — минуты)

Пользователь нажал "Отправить", приложение ушло в фон (звонок, переключение приложений, блокировка экрана). Запрос мог уйти или не уйти — приложение не знает наверняка. При восстановлении из фона разумная стратегия — повторить запрос. Интервал: от нескольких секунд до минут. Блокировка (если она была) давно истекла, но перевод в БД уже создан.

### Offline-first / queue-based клиент (минуты — часы)

Мобильные приложения для денежных переводов часто работают в регионах с нестабильным интернетом. Паттерн: пользователь заполняет форму, нажимает "Отправить", запрос сохраняется в локальную очередь. Когда появляется сеть — очередь начинает отправку. Если первая попытка завершилась таймаутом (сеть пропала снова), запрос остаётся в очереди. Через час сеть появляется, очередь отправляет тот же запрос повторно. Первый раз он мог пройти успешно — клиент просто не получил подтверждение.

### Retry-логика в клиентском SDK / HTTP-библиотеке (секунды)

Многие HTTP-клиенты имеют встроенный retry: OkHttp, Retrofit, axios с interceptors, fetch + retry wrapper. Если разработчик клиента включил retry на 5xx или timeout — запросы будут повторяться автоматически. Сервер не может контролировать, как клиент настроен.

### Webhook / callback retry от внешних сервисов (секунды — часы)

Не относится напрямую к `POST /transfers`, но тот же принцип. Payment provider (Stripe, Adyen) шлёт webhook "payment.captured". Если наш сервер не ответил 200 вовремя — провайдер ретраит с экспоненциальным backoff: через 5с, 30с, 5мин, 1ч. Каждый webhook несёт один и тот же `event_id`, и обработчик должен быть идемпотентным.

### Сводка по временным профилям

| Источник дубликата | Типичная задержка | Кто инициирует повтор |
|---|---|---|
| Двойной клик | < 1с | Пользователь |
| Потеря ответа | 1-10с | Клиентский код |
| ALB/шлюз retry | 3-30с | Инфраструктура |
| Мобильный фон | 10с — 5мин | ОС + приложение |
| Offline-first очередь | 1мин — 24ч | Клиентский код |
| HTTP-библиотека retry | 1-30с | SDK |

Ключевой вывод: дубликаты приходят с задержкой **от миллисекунд до часов**. Один механизм защиты не покрывает весь этот диапазон.

## Архитектура: двухуровневая защита

```
Запрос клиента (с X-Idempotency-Key)
        |
        v
  +-----------------+
  | Consul Lock     |  <-- Уровень 1: распределённая блокировка по отправителю
  | key: sender/{id}/create
  +-----------------+
        |
        v
  +-----------------+
  | DB Lookup       |  <-- Уровень 2: SELECT по idempotency_key
  | transfers table |
  +-----------------+
        |
        v
  (создание transfer + outbox event в одной транзакции)
```

### Уровень 1 — Распределённая блокировка (Consul)

**От чего защищает:** конкурентные дубликаты, приходящие в пределах миллисекунд друг от друга ("двойной клик", быстрый ретрай).

```kotlin
// TransferService.kt
val lockKey = "sender/${command.senderId}/create"

return distributedLockService.executeWithLock(lockKey) {
    // ... idempotency check + бизнес-логика внутри блокировки
}
```

Блокировка привязана к `sender/{senderId}/create`. Это значит:
- Два запроса от **одного отправителя** сериализуются
- Запросы от **разных отправителей** выполняются параллельно (нет глобального bottleneck)

Consul-реализация использует session-based блокировку с TTL auto-release как страховку:

```kotlin
// ConsulDistributedLockService.kt
private fun acquireLock(key: String, sessionId: String) {
    val deadline = System.currentTimeMillis() + properties.acquireTimeoutMs
    var retryInterval = properties.retryIntervalMs

    while (true) {
        val acquired = consulClient.setKVValue(key, "locked", putParams).value
        if (acquired) return
        if (System.currentTimeMillis() >= deadline) {
            destroySession(sessionId)
            throw DistributedLockException(key)
        }
        Thread.sleep(retryInterval)
        retryInterval = (retryInterval * 2).coerceAtMost(500) // exponential backoff
    }
}
```

### Уровень 2 — Проверка идемпотентности в БД

**От чего защищает:** отложенные дубликаты, приходящие после того как блокировка уже отпущена (секунды, минуты, часы спустя).

```kotlin
// Внутри блокировки:
val existingTransfer = transferRepository.findByIdempotencyKey(command.idempotencyKey)
if (existingTransfer != null) {
    log.info("Idempotency hit: key=${command.idempotencyKey}")
    return@executeWithLock Pair(TransferWithRecipient(existingTransfer, recipient), false)
}
```

За этим стоит UNIQUE constraint в БД как последний рубеж:

```sql
-- V001__create_transfers_table.sql
idempotency_key UUID NOT NULL,
CONSTRAINT uq_transfers_idempotency_key UNIQUE (idempotency_key),
```

Даже если проверка на уровне приложения каким-то образом пропустит дубликат (race condition при гипотетическом баге), БД отклонит дублирующий INSERT с constraint violation.

## Почему нужны оба уровня

| Сценарий | Только блокировка | Только DB-проверка | Блокировка + DB |
|---|---|---|---|
| Двойной клик (< 100мс) | Сериализовано, второй ждёт и видит результат первого | Оба запроса параллельно, один падает на UNIQUE constraint (грязный 409/500) | Сериализовано, второй получает чистый ответ (200) |
| Ретрай шлюза через 2с | Блокировка уже отпущена, второй запрос создаёт дубликат | Пойман через `findByIdempotencyKey`, возвращает существующий | Пойман DB-проверкой внутри блокировки |
| Мобильный ретрай через 30мин | Блокировка давно истекла, нет защиты | Пойман через `findByIdempotencyKey` | Пойман DB-проверкой |
| Два инстанса приложения, одна миллисекунда | Блокировка сериализует между инстансами (распределённая) | Гонка на INSERT, один получает constraint violation | Сериализовано, чистый ответ |

**Ключевой инсайт:** блокировка решает проблему *времени* (конкурентные запросы), а DB-проверка решает проблему *персистентности* (отложенные запросы). Ни одна из них по отдельности не покрывает оба случая.

## Рассмотренные альтернативы

### 1. Только UNIQUE constraint (без блокировки, без проверки в приложении)

```sql
CONSTRAINT uq_transfers_idempotency_key UNIQUE (idempotency_key)
```

- Полагается на перехват `DataIntegrityViolationException` и возврат существующего трансфера
- Работает, но error path становится "нормальным" путём для ретраев
- Сложнее отличить "настоящий дубликат" от "реальный баг целостности данных"
- Ответ первого запроса нужно реконструировать или перечитать — лишняя сложность

### 2. SELECT ... FOR UPDATE (пессимистичная блокировка на уровне строки)

```sql
SELECT * FROM transfers WHERE idempotency_key = ? FOR UPDATE
```

- Работает только если строка уже существует (нельзя заблокировать то, что ещё не создано)
- Для гонки первый-запрос-vs-первый-запрос нужны advisory locks или отдельная таблица блокировок
- Плохо работает при операциях с несколькими таблицами (transfer + outbox в одной TX)

### 3. PostgreSQL Advisory Locks

```sql
SELECT pg_advisory_xact_lock(hashtext(?))
```

- Работают на уровне БД (между инстансами приложения, в отличие от in-process блокировок)
- Но привязаны к одному инстансу PostgreSQL (нет защиты при масштабировании на несколько нод БД)
- Возможны коллизии хешей (хотя маловероятны)
- У нас уже есть Consul для service discovery — Consul-блокировки ложатся естественно

### 4. Redis SETNX (часто встречается в туториалах)

```
SET lock:sender:{id} NX EX 10
```

- Быстро, хорошо изученный паттерн
- Но требует аккуратной обработки clock skew и Redlock для multi-node Redis
- У нас уже был Consul в стеке; Redis-as-lock означал бы два distributed state системы

## Принятое решение

Выбрали **Consul distributed lock + проверка в БД на уровне приложения + UNIQUE constraint** потому что:

1. **Consul уже был в стеке** для service discovery — не нужна новая инфраструктура
2. **Session TTL auto-release** предотвращает deadlock при крэше приложения с удержанной блокировкой
3. **Per-sender lock key** минимизирует contention (нет глобальной блокировки)
4. **DB lookup** покрывает все сценарии отложенных ретраев без опоры на обработку ошибок
5. **UNIQUE constraint** — последняя линия обороны, defense in depth

Интерфейс `DistributedLockService` позволяет подменять реализацию:
- `ConsulDistributedLockService` — для продакшена
- `NoOpDistributedLockService` — для тестов (не нужна зависимость от Consul)

## Главный вывод

Идемпотентность — это не один механизм, а многослойная стратегия. Каждый слой покрывает режимы отказов, которые другие покрыть не могут:

- **Распределённая блокировка** = предотвращает конкурентное выполнение (быстрые дубликаты)
- **Проверка в БД на уровне приложения** = обнаруживает ранее завершённые запросы (медленные дубликаты), возвращает чистый ответ
- **UNIQUE constraint** = абсолютная гарантия на уровне хранилища (defense in depth)

В системе денежных переводов "скорее всего не продублирует" — неприемлемо. Стоимость двойного списания многократно превышает стоимость избыточной проверки.
