# HTTP Status Codes: 400 vs 422

## Контекст

В transfer-service бизнес-исключения (например, `UnsupportedCorridorException`) возвращают HTTP **422**, а не 400. Важно понимать разницу.

## 400 Bad Request

Запрос **синтаксически** некорректен — сервер не может его распарсить или обязательные поля отсутствуют.

Примеры:
- Невалидный JSON (`{ "amount": }`)
- Пропущено обязательное поле (`send_currency` отсутствует)
- Неверный тип данных (`"amount": "abc"` вместо числа)
- Нарушение `@Valid` аннотаций (Bean Validation: `@NotNull`, `@Size`, `@Pattern`)

## 422 Unprocessable Entity (RFC 9110)

Запрос **синтаксически** корректен (JSON валидный, все поля на месте, типы верные), но **семантически** не может быть обработан — нарушено бизнес-правило.

Примеры в нашем проекте:
- `UnsupportedCorridorException` — коридор `US_JP` не поддерживается
- `UnsupportedDeliveryMethodException` — `CASH_PICKUP` недоступен для `GB_IN`
- `MinimumAmountException` — сумма ниже минимума для коридора
- `QuoteCorridorMismatchException` — валюты в quote не совпадают с запросом

## Почему это важно

Разделение 400/422 помогает клиенту понять **характер ошибки**:
- **400** — "ты отправил мусор, проверь формат запроса"
- **422** — "запрос правильный, но бизнес-логика не позволяет это сделать"

Это особенно полезно в связке с **RFC 9457 (Problem Details)**, который мы используем в `GlobalExceptionHandler` — клиент получает структурированный ответ с `type`, `title`, `detail` и дополнительными полями.

## Где используется

- `GlobalExceptionHandler` маппит наши кастомные исключения на соответствующие HTTP-коды
- Каждое бизнес-исключение наследует базовый класс и указывает `statusCode = 422`
- Bean Validation ошибки (`@Valid`) автоматически возвращают 400 через Spring
