## ЧАСТЬ 1. JAVA CORE

---

### 1.1. Основы языка и платформы

**В: Что такое JVM, JRE и JDK? В чём разница?**

О: JDK (Java Development Kit) — это полный набор инструментов для разработки на Java. Он включает в себя компилятор `javac`, отладчик `jdb`, инструмент для создания документации `javadoc`, а также само JRE. JRE (Java Runtime Environment) — среда выполнения, которая включает JVM и набор стандартных библиотек (rt.jar и др.), необходимых для запуска скомпилированных Java-программ. JVM (Java Virtual Machine) — виртуальная машина, которая непосредственно исполняет байт-код. Она отвечает за загрузку классов (ClassLoader), управление памятью (Garbage Collection), JIT-компиляцию (перевод часто исполняемого байт-кода в нативный машинный код) и обеспечение безопасности через Security Manager. Ключевой принцип — «Write Once, Run Anywhere»: один и тот же .class файл исполняется на любой платформе, где есть JVM.

**В: Как работает компиляция и выполнение Java-программы?**

О: Процесс состоит из нескольких этапов. Сначала исходный код (.java файлы) компилируется компилятором `javac` в байт-код (.class файлы). Байт-код — это платформенно-независимый промежуточный код для JVM. При запуске программы JVM загружает .class файлы через систему ClassLoader. Далее bytecode verifier проверяет байт-код на корректность и безопасность: нет ли нарушений типизации, не происходит ли выход за пределы стека. После верификации интерпретатор JVM начинает последовательно исполнять байт-код. Одновременно с этим JIT-компилятор (Just-In-Time) отслеживает «горячие» методы — те, которые вызываются часто — и компилирует их в нативный машинный код для конкретной платформы. Это даёт существенный прирост производительности. Современные JVM (HotSpot) используют многоуровневую компиляцию: сначала C1-компилятор производит быструю оптимизацию, затем C2 — более агрессивную, но и более затратную.

**В: Что такое ClassLoader и какие виды существуют?**

О: ClassLoader — это подсистема JVM, которая отвечает за загрузку .class файлов в память. Существует иерархия из трёх основных ClassLoader'ов. Bootstrap ClassLoader — самый верхний, написан на нативном коде, загружает классы из rt.jar (java.lang, java.util и т.д.). Platform (Extension) ClassLoader — загружает классы расширений из директории lib/ext. Application (System) ClassLoader — загружает классы из classpath приложения. Работает принцип делегирования (parent delegation model): когда Application ClassLoader получает запрос на загрузку класса, он сначала делегирует запрос родителю (Platform), тот — своему родителю (Bootstrap). Класс загружается тем загрузчиком, который первый нашёл его. Если никто не нашёл — выбрасывается ClassNotFoundException. Можно создавать собственные ClassLoader'ы, наследуя java.lang.ClassLoader и переопределяя метод findClass(). Это используется в серверах приложений (Tomcat, WildFly) для изоляции приложений, в OSGi-контейнерах, а также для горячей перезагрузки классов.

**В: Какие примитивные типы данных есть в Java?**

О: В Java 8 примитивных типов. byte — 8 бит, диапазон от -128 до 127. short — 16 бит, от -32768 до 32767. int — 32 бита, от -2^31 до 2^31-1 (примерно ±2.1 миллиарда). long — 64 бита, от -2^63 до 2^63-1. float — 32-битное число с плавающей точкой (IEEE 754), точность около 6-7 значащих цифр. double — 64-битное число с плавающей точкой, точность около 15-16 значащих цифр. char — 16-битный беззнаковый тип для символов Unicode (от 0 до 65535). boolean — логический тип, true или false; его размер не определён спецификацией однозначно, но в массивах обычно занимает 1 байт. Важно помнить, что примитивы хранятся в стеке (если это локальные переменные) и передаются по значению. Для каждого примитива существует класс-обёртка (Integer, Long, Double и т.д.), и начиная с Java 5 работает автоупаковка и автораспаковка (autoboxing/unboxing). Для финансовых вычислений нельзя использовать float/double из-за потери точности — следует использовать BigDecimal.

**В: Чем отличается == от equals()? Контракт equals() и hashCode().**

О: Оператор `==` для примитивов сравнивает значения, а для ссылочных типов — сравнивает ссылки, то есть проверяет, указывают ли две переменные на один и тот же объект в памяти. Метод `equals()` предназначен для логического сравнения содержимого объектов. По умолчанию в классе Object метод equals() работает как ==, но его можно и нужно переопределять в своих классах.

Контракт equals(): рефлексивность (x.equals(x) == true), симметричность (если x.equals(y), то y.equals(x)), транзитивность (если x.equals(y) и y.equals(z), то x.equals(z)), согласованность (многократные вызовы дают одинаковый результат, если объекты не менялись), для любого не-null x: x.equals(null) == false.

Контракт hashCode(): если два объекта равны по equals(), их hashCode() обязан быть одинаковым. Если два объекта не равны, hashCode() может как совпадать, так и различаться (коллизии допустимы, но нежелательны). Если переопределяете equals(), обязаны переопределить и hashCode(). Нарушение этого контракта приводит к некорректной работе HashMap, HashSet и других коллекций, основанных на хэш-таблицах: объект, добавленный в HashSet, может быть «потерян» при поиске.

**В: Что такое String Pool? Неизменяемость строк.**

О: String Pool (пул строк) — это специальная область в памяти кучи (heap), где JVM хранит уникальные экземпляры строковых литералов. Когда вы пишете `String s = "hello"`, JVM сначала проверяет, есть ли строка "hello" в пуле. Если есть — возвращает ссылку на существующий объект. Если нет — создаёт новый объект в пуле. Поэтому `"hello" == "hello"` вернёт true — это одна и та же ссылка. Но `new String("hello")` всегда создаёт новый объект в куче, вне пула. Метод `intern()` позволяет явно поместить строку в пул.

Неизменяемость (immutability) означает, что после создания объект String нельзя изменить. Массив char[] внутри String помечен как final и private, и нет методов, которые бы его модифицировали. Любая «модификация» строки (конкатенация, replace, substring) создаёт новый объект. Неизменяемость обеспечивает: потокобезопасность (строки можно безопасно использовать в многопоточной среде без синхронизации), безопасное использование как ключей в HashMap (hashCode не изменится), кэширование hashCode (вычисляется один раз при первом вызове и запоминается), безопасность в контексте загрузки классов и сетевых соединений. Для частых конкатенаций в цикле нужно использовать StringBuilder (не потокобезопасный, но быстрый) или StringBuffer (потокобезопасный, но медленнее из-за синхронизации).

**В: Что такое autoboxing и unboxing? Какие подводные камни?**

О: Autoboxing — автоматическое преобразование примитива в соответствующий объект-обёртку (int → Integer). Unboxing — обратный процесс (Integer → int). Введены в Java 5.

Подводные камни: NullPointerException при unboxing'е null (Integer a = null; int b = a; — NPE). Производительность: в цикле `Long sum = 0L; for(int i=0; i<N; i++) sum += i;` на каждой итерации создаётся новый объект Long — катастрофически медленно. Кэширование: Integer кэширует значения от -128 до 127 (IntegerCache), поэтому `Integer.valueOf(127) == Integer.valueOf(127)` вернёт true, а `Integer.valueOf(128) == Integer.valueOf(128)` — false. Это одна из самых коварных ловушек на собеседованиях. Такое же кэширование есть у Byte, Short, Long, Character (для значений 0-127).

### 1.2. Объектно-ориентированное программирование

**В: Назовите и объясните 4 принципа ООП.**

О: Инкапсуляция — это механизм сокрытия внутренней реализации объекта и предоставления доступа к данным только через определённые методы (геттеры, сеттеры). В Java реализуется через модификаторы доступа (private, protected, default, public). Цель — защита данных от некорректного использования и уменьшение связанности между компонентами.

Наследование — механизм создания нового класса на основе существующего. Дочерний класс (подкласс) получает все поля и методы родителя и может добавлять свои или переопределять родительские. В Java наследование классов одиночное (extends), но можно реализовать множество интерфейсов (implements). Наследование обеспечивает повторное использование кода и иерархию типов.

Полиморфизм — способность объектов разных типов обрабатываться через общий интерфейс. Существует два вида: compile-time (статический) — перегрузка методов (overloading), когда методы с одним именем имеют разные параметры; runtime (динамический) — переопределение методов (overriding), когда подкласс предоставляет свою реализацию метода родителя, и конкретная реализация выбирается во время выполнения на основе реального типа объекта (механизм virtual method dispatch).

Абстракция — выделение существенных характеристик объекта, отделяющих его от других объектов. В Java реализуется через абстрактные классы и интерфейсы. Позволяет работать с объектами на уровне концепций, не зная деталей реализации.

**В: Разница между абстрактным классом и интерфейсом?**

О: Абстрактный класс может содержать как абстрактные методы (без реализации), так и конкретные (с реализацией). Может иметь конструкторы, поля с любым модификатором доступа, статические методы. Класс может наследоваться только от одного абстрактного класса. Используется, когда есть общая реализация, которую нужно разделить между связанными классами.

Интерфейс — контракт, определяющий набор методов. До Java 8 мог содержать только абстрактные методы и константы (public static final). Начиная с Java 8 может содержать default-методы (с реализацией по умолчанию) и static-методы. С Java 9 — ещё и private-методы. Класс может реализовывать множество интерфейсов. Поля в интерфейсе всегда public static final. Нет конструкторов. Используется для определения контракта, который могут реализовать несвязанные классы.

Принцип выбора: если нужна общая реализация и есть отношение «является» (is-a) — абстрактный класс. Если нужен контракт поведения «может делать» (can-do) — интерфейс. Начиная с Java 8 граница стала менее чёткой благодаря default-методам, но общее правило сохраняется.

**В: Что такое SOLID-принципы?**

О: S — Single Responsibility Principle (Принцип единственной ответственности): у класса должна быть одна причина для изменения. Класс должен отвечать за одну и только одну задачу. Например, класс User не должен содержать логику отправки email — для этого нужен отдельный EmailService.

O — Open/Closed Principle (Принцип открытости/закрытости): классы должны быть открыты для расширения, но закрыты для модификации. Новая функциональность добавляется через наследование или реализацию интерфейсов, а не путём изменения существующего кода.

L — Liskov Substitution Principle (Принцип подстановки Барбары Лисков): объекты подкласса должны быть взаимозаменяемы с объектами суперкласса без нарушения корректности программы. Классический контрпример: если Square наследует Rectangle, то setWidth() может нарушить инварианты Rectangle.

I — Interface Segregation Principle (Принцип разделения интерфейсов): клиенты не должны зависеть от методов, которые они не используют. Лучше много специализированных интерфейсов, чем один «толстый».

D — Dependency Inversion Principle (Принцип инверсии зависимостей): модули верхнего уровня не должны зависеть от модулей нижнего уровня. Оба должны зависеть от абстракций. Абстракции не должны зависеть от деталей. Это основа для Dependency Injection.

### 1.3. Обработка исключений

**В: Иерархия исключений в Java. Checked vs Unchecked.**

О: На вершине иерархии — класс Throwable. От него наследуются Error и Exception.

Error — серьёзные проблемы, с которыми приложение обычно не может справиться: OutOfMemoryError, StackOverflowError, NoClassDefFoundError. Их не нужно ловить.

Exception делится на два типа. Checked exceptions — наследники Exception, но не RuntimeException: IOException, SQLException, ClassNotFoundException. Компилятор требует их обработки: либо try-catch, либо объявление в throws. Unchecked exceptions — наследники RuntimeException: NullPointerException, IllegalArgumentException, ArrayIndexOutOfBoundsException, ClassCastException. Компилятор не требует их явной обработки.

Checked исключения сигнализируют о внешних проблемах (файл не найден, БД недоступна), которые вызывающий код может осмысленно обработать. Unchecked — об ошибках программирования, которые нужно исправлять в коде. В современных фреймворках (Spring) есть тенденция к использованию unchecked исключений (Spring оборачивает JDBC-исключения в DataAccessException, который unchecked).

**В: Как работает try-with-resources?**

О: Конструкция try-with-resources (Java 7+) автоматически закрывает ресурсы, реализующие интерфейс AutoCloseable. Синтаксис: `try (InputStream is = new FileInputStream("file")) { ... }`. После выхода из блока try (нормально или через исключение) вызывается is.close(). Если в блоке try и при закрытии ресурса возникли исключения, то основным будет исключение из try, а исключение из close() добавляется как suppressed (доступно через getSuppressed()). Ресурсы закрываются в порядке, обратном объявлению. С Java 9 можно использовать effectively final переменные, объявленные до try: `InputStream is = ...; try (is) { ... }`. Это гораздо надёжнее ручного закрытия в finally, где легко забыть обработать исключение при закрытии или нарушить порядок.

### 1.4. Коллекции (Collections Framework)

**В: Опишите иерархию Collections Framework.**

О: Корневой интерфейс — Iterable, от него наследуется Collection. От Collection наследуются три ключевых интерфейса: List (упорядоченная коллекция с доступом по индексу), Set (коллекция уникальных элементов), Queue (очередь с порядком обработки). Отдельно стоит интерфейс Map (коллекция пар ключ-значение), не наследующий Collection.

List: ArrayList (внутри динамический массив, быстрый random access O(1), вставка/удаление из середины O(n)), LinkedList (двусвязный список, вставка/удаление O(1) при наличии итератора, random access O(n)), Vector (устаревший потокобезопасный аналог ArrayList), CopyOnWriteArrayList (потокобезопасный, создаёт копию массива при каждом изменении — подходит для частого чтения и редкой записи).

Set: HashSet (на основе HashMap, O(1) в среднем, без гарантии порядка), LinkedHashSet (сохраняет порядок вставки), TreeSet (на основе TreeMap, красно-чёрное дерево, O(log n), элементы отсортированы), EnumSet (высокопроизводительный Set для enum, основан на битовых масках).

Queue: PriorityQueue (на основе бинарной кучи, элементы извлекаются по приоритету), ArrayDeque (двусторонняя очередь на основе массива, быстрее LinkedList для реализации стека и очереди), LinkedList (реализует и List, и Deque).

Map: HashMap (O(1) средний случай, допускает один null-ключ и null-значения), LinkedHashMap (сохраняет порядок вставки или доступа — можно использовать для LRU-кэша), TreeMap (красно-чёрное дерево, O(log n), ключи отсортированы), Hashtable (устаревший, потокобезопасный, не допускает null), ConcurrentHashMap (потокобезопасный, сегментированные блокировки, высокая производительность при конкурентном доступе), EnumMap (ключи — enum, массив внутри).

**В: Как работает HashMap внутри?**

О: HashMap — это массив бакетов (Node[] table). При добавлении элемента: вычисляется hashCode() ключа, затем вычисляется индекс бакета: `index = hash(key) & (capacity - 1)`. Функция hash() дополнительно перемешивает биты hashCode, чтобы уменьшить коллизии. Если бакет пуст — создаётся нода и помещается туда. Если бакет занят — сравниваются хэши и equals() ключей. Если ключ совпадает — значение заменяется. Если не совпадает — это коллизия, и нода добавляется в связный список или дерево.

Начиная с Java 8, когда количество элементов в одном бакете превышает TREEIFY_THRESHOLD (8), связный список преобразуется в красно-чёрное дерево, что меняет worst case с O(n) на O(log n). Обратное преобразование (untreeify) происходит при уменьшении до 6 элементов.

Начальная ёмкость по умолчанию — 16, load factor — 0.75. Когда количество элементов превышает capacity * loadFactor (порог = 12 при дефолтных настройках), происходит рехэширование: размер массива удваивается, все элементы перераспределяются. Рехэширование — дорогая операция O(n), поэтому если заранее известно количество элементов, лучше указать начальную ёмкость: `new HashMap<>(expectedSize * 4 / 3 + 1)`.

**В: Чем отличается HashMap от ConcurrentHashMap?**

О: HashMap не потокобезопасен. Одновременная модификация из нескольких потоков может привести к бесконечному циклу (в Java 7 при рехэшировании) или потере данных. Collections.synchronizedMap() оборачивает в synchronized, но блокирует всю карту — плохая производительность.

ConcurrentHashMap (Java 8+) использует тонкую гранулярность блокировок: блокируется только конкретный бакет (нода), а не вся таблица. Используется CAS (Compare-And-Swap) для неблокирующих операций. Не допускает null ни в ключах, ни в значениях (в отличие от HashMap). Итератор — weakly consistent: видит состояние на момент создания, не бросает ConcurrentModificationException. Предоставляет атомарные операции: putIfAbsent(), compute(), computeIfAbsent(), merge(). Поддерживает параллельные bulk-операции: forEach(), reduce(), search() с параметром параллелизма.

**В: Что такое fail-fast и fail-safe итераторы?**

О: Fail-fast итераторы (ArrayList, HashMap и большинство стандартных коллекций) бросают ConcurrentModificationException, если коллекция была структурно изменена после создания итератора (не через сам итератор). Реализуется через счётчик модификаций modCount: итератор запоминает его значение при создании и проверяет при каждом вызове next(). Это best-effort поведение — не гарантируется в 100% случаев.

Fail-safe итераторы (ConcurrentHashMap, CopyOnWriteArrayList) работают на копии коллекции или используют отложенную консистентность. Не бросают ConcurrentModificationException. Могут не отражать модификации, произошедшие после создания итератора.

**В: Когда использовать ArrayList, а когда LinkedList?**

О: Почти всегда ArrayList. LinkedList теоретически лучше для вставки/удаления в начало или середину списка, но на практике ArrayList быстрее почти во всех сценариях благодаря кэш-дружественности процессора (элементы лежат в непрерывной области памяти). LinkedList потребляет значительно больше памяти: каждый элемент — отдельный объект Node с двумя ссылками (prev, next), плюс overhead объекта. LinkedList может быть оправдан только если нужна частая вставка/удаление при обходе через итератор (но не по индексу), а размер списка очень велик.

### 1.5. Generics (Обобщения)

**В: Что такое generics и зачем они нужны?**

О: Generics позволяют параметризировать классы, интерфейсы и методы типами. Обеспечивают типобезопасность на этапе компиляции, устраняя необходимость явного приведения типов. Например, `List<String>` гарантирует, что в список можно добавить только String, а при получении элемента не нужен каст.

Type Erasure — механизм реализации: компилятор проверяет типы, вставляет необходимые касты, а затем стирает информацию о типовых параметрах. На уровне байт-кода `List<String>` и `List<Integer>` — это одинаковый `List`. Последствия: нельзя использовать примитивы как типовые параметры (`List<int>` — нельзя, только `List<Integer>`); нельзя создать массив обобщённого типа (`new T[]` — нельзя); нельзя использовать instanceof с обобщёнными типами; нельзя создать экземпляр типового параметра (`new T()` — нельзя без явной передачи Class<T>).

**В: Что такое wildcards? Разница между <? extends T> и <? super T>?**

О: Wildcards — символы подстановки для гибкости при работе с обобщёнными типами.

`<? extends T>` (Upper Bounded Wildcard) — «что-то, являющееся T или его подтипом». Можно читать элементы как T, но нельзя добавлять (кроме null), потому что компилятор не знает точный тип. `List<? extends Number>` может быть List<Integer>, List<Double> и т.д. — вставлять нельзя, но можно читать как Number.

`<? super T>` (Lower Bounded Wildcard) — «что-то, являющееся T или его супертипом». Можно добавлять элементы типа T и его подтипов, но читать можно только как Object. `List<? super Integer>` может быть List<Integer>, List<Number>, List<Object> — можно вставлять Integer, но при чтении получаем Object.

Правило PECS (Producer Extends, Consumer Super): если коллекция — источник данных (producer) — используйте extends; если коллекция — приёмник данных (consumer) — используйте super. Например, в `Collections.copy(List<? super T> dest, List<? extends T> src)`: src — источник (extends), dest — приёмник (super).

### 1.6. Многопоточность и конкурентность

**В: Способы создания потоков в Java.**

О: Наследование от Thread: создать класс, наследующий Thread, переопределить метод run(), создать экземпляр и вызвать start(). Ограничение — Java не поддерживает множественное наследование, поэтому класс не сможет наследоваться от другого класса.

Реализация Runnable: создать класс, реализующий интерфейс Runnable (или передать лямбду), передать его в конструктор Thread. Более гибкий подход — класс может наследоваться от другого класса.

Реализация Callable: аналогично Runnable, но метод call() возвращает результат и может бросать checked-исключения. Используется с ExecutorService.submit(), который возвращает Future для получения результата.

ExecutorService: предпочтительный способ в production-коде. Пулы потоков создаются через Executors: newFixedThreadPool(n), newCachedThreadPool(), newSingleThreadExecutor(), newScheduledThreadPool(n). Или напрямую через ThreadPoolExecutor для тонкой настройки (corePoolSize, maximumPoolSize, keepAliveTime, workQueue).

CompletableFuture (Java 8+): асинхронное программирование с композицией. supplyAsync(), thenApply(), thenCompose(), thenCombine(), exceptionally(), allOf(), anyOf(). Позволяет строить цепочки асинхронных операций без блокировок.

**В: Жизненный цикл потока (Thread states).**

О: NEW — поток создан (new Thread()), но ещё не запущен. RUNNABLE — после вызова start(); поток либо выполняется, либо готов к выполнению (ожидает процессорное время). BLOCKED — поток пытается войти в synchronized-блок, который уже занят другим потоком; ожидает освобождения монитора. WAITING — поток находится в неограниченном ожидании: вызван Object.wait() без таймаута, Thread.join() без таймаута, или LockSupport.park(). TIMED_WAITING — ограниченное ожидание: Thread.sleep(ms), Object.wait(ms), Thread.join(ms), LockSupport.parkNanos(). TERMINATED — поток завершил выполнение (метод run() завершился нормально или с исключением).

**В: Что такое synchronized? Мониторы и блокировки.**

О: Ключевое слово synchronized обеспечивает взаимное исключение (mutual exclusion) и видимость изменений (happens-before). Каждый объект в Java имеет связанный монитор (intrinsic lock). Только один поток может владеть монитором объекта в любой момент.

Synchronized-метод: `synchronized void method()` — монитор на this для instance-методов, на Class-объект для static-методов. Synchronized-блок: `synchronized(lockObject) { ... }` — более гранулярный контроль, блокировка на конкретный объект.

Монитор реентерабелен (reentrant): если поток уже владеет монитором, он может повторно войти в synchronized-блок на тот же объект (внутренний счётчик увеличивается). Synchronized гарантирует: атомарность (в блок входит только один поток), видимость (все изменения, сделанные в блоке, видны следующему потоку, получившему монитор), happens-before (запись в синхронизированном блоке happens-before чтения в последующем синхронизированном блоке на тот же монитор).

**В: Что такое volatile?**

О: Модификатор volatile гарантирует: видимость (запись в volatile-переменную немедленно видна всем потокам — сбрасывает кэш процессора в основную память); happens-before (запись в volatile happens-before последующего чтения этой переменной любым потоком); запрет переупорядочивания инструкций (memory barrier). Volatile НЕ обеспечивает атомарность составных операций: volatile int counter; counter++ — не атомарна (read-modify-write). Для атомарных операций нужны AtomicInteger, AtomicLong и т.д. Volatile подходит для простых флагов (boolean running), для паттерна double-checked locking (в Singleton), для publication гарантий (передачи ссылки на объект между потоками).

**В: Объясните пакет java.util.concurrent (JUC).**

О: Locks: ReentrantLock — аналог synchronized, но с дополнительными возможностями: tryLock() (попытка захвата без блокировки), lockInterruptibly() (прерываемая блокировка), fairness (справедливый порядок — потоки получают блокировку в порядке ожидания), Condition (несколько условий ожидания на одном lock'е). ReadWriteLock — раздельные блокировки для чтения и записи: множество читателей одновременно, но только один писатель. StampedLock (Java 8) — оптимистичные блокировки чтения для ещё большей производительности.

Atomic-классы: AtomicInteger, AtomicLong, AtomicReference — атомарные операции через CAS (Compare-And-Swap) без блокировок. Методы: incrementAndGet(), compareAndSet(), getAndUpdate(). LongAdder — быстрее AtomicLong при высокой конкуренции за счёт сегментирования.

Синхронизаторы: CountDownLatch — одноразовый барьер, потоки ожидают, пока счётчик достигнет нуля. CyclicBarrier — многоразовый барьер, все потоки ожидают друг друга. Semaphore — ограничивает количество одновременных доступов к ресурсу. Phaser — гибкая замена CountDownLatch и CyclicBarrier.

Concurrent collections: ConcurrentHashMap, ConcurrentLinkedQueue, ConcurrentLinkedDeque, CopyOnWriteArrayList, CopyOnWriteArraySet, BlockingQueue (ArrayBlockingQueue, LinkedBlockingQueue, PriorityBlockingQueue).

**В: Что такое deadlock? Как избежать?**

О: Deadlock — взаимная блокировка, когда два или более потоков навечно ожидают друг друга, каждый удерживая ресурс, нужный другому. Классический пример: поток A захватил lock1 и ждёт lock2, а поток B захватил lock2 и ждёт lock1.

Четыре условия возникновения (все должны выполняться одновременно): взаимное исключение (ресурс эксклюзивен), удержание и ожидание (поток удерживает ресурс, ожидая другой), невытеснение (ресурс не может быть отобран), циклическое ожидание (циклическая цепь зависимостей).

Способы предотвращения: упорядочивание захвата блокировок (всегда захватывать в одном и том же глобальном порядке — устраняет циклическое ожидание); использование tryLock() с таймаутом; минимизация области синхронизации; использование высокоуровневых конкурентных структур вместо ручных блокировок; обнаружение через ThreadMXBean.findDeadlockedThreads() или JStack. Livelock — потоки активны, но не продвигаются (каждый уступает другому). Starvation — поток не получает ресурс из-за приоритетов или несправедливого планирования.

**В: Что такое ThreadLocal?**

О: ThreadLocal предоставляет каждому потоку собственную независимую копию переменной. Каждый поток видит и модифицирует только свою копию. Внутренне: каждый Thread содержит ThreadLocalMap, где ключ — WeakReference на ThreadLocal, а значение — данные потока.

Применение: хранение контекста пользователя (SecurityContext, locale), хранение соединений с БД (Connection per thread), SimpleDateFormat (не потокобезопасен — каждому потоку свой), транзакционный контекст.

Важная проблема: утечка памяти при использовании с пулами потоков. Поток из пула не уничтожается, и данные в ThreadLocal остаются. Обязательно вызывать threadLocal.remove() после использования (обычно в finally-блоке). InheritableThreadLocal — наследует значение из родительского потока в дочерний.

### 1.7. Stream API и функциональное программирование (Java 8+)

**В: Что такое Stream API? Основные операции.**

О: Stream — последовательность элементов, поддерживающая последовательную и параллельную обработку. Не хранит данные, не модифицирует источник, ленив (intermediate-операции выполняются только при вызове terminal-операции).

Создание: collection.stream(), Arrays.stream(arr), Stream.of(elements), Stream.generate(supplier), Stream.iterate(seed, operator), IntStream.range(0, 100), Files.lines(path).

Промежуточные (intermediate) — возвращают новый Stream: filter(predicate), map(function), flatMap(function), distinct(), sorted(), peek(consumer), limit(n), skip(n).

Терминальные (terminal) — запускают конвейер: forEach(consumer), collect(collector), reduce(identity, accumulator), count(), min(comparator), max(comparator), anyMatch(predicate), allMatch(predicate), noneMatch(predicate), findFirst(), findAny(), toArray().

Collectors: toList(), toSet(), toMap(), groupingBy(), partitioningBy(), joining(), counting(), summarizingInt(), toUnmodifiableList() (Java 10).

Параллельные стримы: parallelStream() или stream().parallel(). Используют ForkJoinPool.commonPool(). Осторожно: не всегда быстрее (overhead на разделение и объединение), проблемы с порядком, сложности при работе с не потокобезопасными коллекторами, побочные эффекты запрещены.

**В: Что такое Optional? Как правильно использовать?**

О: Optional<T> — контейнер, который может содержать или не содержать значение. Введён для борьбы с NullPointerException. Создание: Optional.of(value) — бросает NPE если null; Optional.ofNullable(value) — допускает null; Optional.empty() — пустой.

Правильное использование: возвращаемый тип методов, которые могут не найти результат. Методы: isPresent(), isEmpty() (Java 11), get() (бросает NoSuchElementException если пуст — избегать), orElse(default), orElseGet(supplier), orElseThrow(), ifPresent(consumer), ifPresentOrElse(consumer, runnable) (Java 9), map(function), flatMap(function), filter(predicate), or(supplier) (Java 9).

Антипаттерны: не использовать как параметр метода, не использовать для полей класса, не вызывать get() без проверки, не оборачивать коллекции в Optional (пустая коллекция лучше).

**В: Что такое функциональные интерфейсы? Основные из java.util.function.**

О: Функциональный интерфейс — интерфейс с одним абстрактным методом (может иметь default и static методы). Аннотация @FunctionalInterface необязательна, но рекомендуется.

Основные: `Function<T,R>` — принимает T, возвращает R (метод apply); `Predicate<T>` — принимает T, возвращает boolean (method test); `Consumer<T>` — принимает T, ничего не возвращает (метод accept); `Supplier<T>` — ничего не принимает, возвращает T (метод get); `UnaryOperator<T>` — Function<T,T>; `BinaryOperator<T>` — BiFunction<T,T,T>; `BiFunction<T,U,R>` — два аргумента; `BiPredicate<T,U>` — два аргумента, boolean; `BiConsumer<T,U>` — два аргумента, void.

Лямбда-выражения — краткая запись анонимной реализации функционального интерфейса: `(x, y) -> x + y`. Method references — ещё более краткая запись: `String::toUpperCase` (ссылка на метод экземпляра), `System.out::println` (ссылка на метод конкретного объекта), `Integer::parseInt` (ссылка на статический метод), `ArrayList::new` (ссылка на конструктор).

### 1.8. Работа с памятью и Garbage Collection

**В: Структура памяти JVM.**

О: Heap (куча) — область для хранения объектов. Разделена на поколения: Young Generation (Eden + два Survivor spaces S0 и S1) — новые объекты; Old Generation (Tenured) — объекты, пережившие несколько сборок мусора. Metaspace (с Java 8, заменила PermGen) — метаданные классов, пул строковых литералов. Размер управляется -Xms (начальный heap), -Xmx (максимальный heap), -XX:MetaspaceSize.

Stack — у каждого потока свой стек. Хранит фреймы методов: локальные переменные, ссылки, промежуточные результаты вычислений, адрес возврата. LIFO-структура. Размер задаётся -Xss.

Program Counter Register — у каждого потока свой, хранит адрес текущей исполняемой инструкции. Native Method Stack — для нативных (JNI) методов.

**В: Как работает Garbage Collection?**

О: GC автоматически освобождает память объектов, на которые нет ссылок. Основные алгоритмы:

Mark-and-Sweep: фаза Mark — обход графа объектов от корней (GC Roots: локальные переменные, статические переменные, потоки, JNI-ссылки), помечая достижимые объекты. Фаза Sweep — удаление непомеченных объектов.

Generational Collection: основана на гипотезе поколений (большинство объектов живут недолго). Minor GC — сборка Young Generation: новые объекты создаются в Eden; когда Eden заполняется, живые объекты копируются в один из Survivor spaces; объекты, пережившие несколько Minor GC (threshold), промотируются в Old Generation. Major/Full GC — сборка Old Generation (и обычно Young), значительно дольше.

Сборщики мусора: Serial GC — однопоточный, для маленьких приложений. Parallel GC — многопоточный, максимизирует throughput (дефолт до Java 8). G1 GC (Garbage First) — делит heap на регионы, собирает в первую очередь регионы с наибольшим количеством мусора; дефолт с Java 9; предсказуемые паузы. ZGC и Shenandoah — сборщики со сверхнизкими паузами (менее 10 мс), работают конкурентно с приложением, подходят для heap размером в терабайты.

## ЧАСТЬ 2. SPRING FRAMEWORK

### 2.1. Основы Spring

**В: Что такое Spring Framework? Ключевые модули.**

О: Spring — экосистема фреймворков для создания enterprise Java-приложений. Основные модули: Spring Core (IoC-контейнер, DI), Spring MVC (веб-фреймворк на основе Servlet API), Spring Data (абстракция доступа к данным), Spring Security (аутентификация и авторизация), Spring AOP (аспектно-ориентированное программирование), Spring Boot (автоконфигурация, встроенный сервер, стартеры), Spring Cloud (микросервисы, service discovery, config server, circuit breaker).

**В: Что такое IoC (Inversion of Control) и DI (Dependency Injection)?**

О: IoC — принцип, при котором управление созданием и жизненным циклом объектов передаётся контейнеру (фреймворку), а не управляется самим кодом приложения. Вместо того чтобы объект сам создавал свои зависимости (`new ServiceImpl()`), он получает их извне.

DI — конкретная реализация IoC. Зависимости «внедряются» в объект контейнером. Три способа: через конструктор (рекомендуемый — обеспечивает иммутабельность, все зависимости обязательны, легко тестировать, поддерживает final-поля); через сеттер (для опциональных зависимостей); через поле (через @Autowired на поле — не рекомендуется: невозможно сделать поле final, сложно тестировать без Spring-контекста).

Spring IoC Container — ApplicationContext — главный контейнер. Он создаёт бины (объекты), разрешает зависимости между ними и управляет их жизненным циклом. Конфигурируется через: XML (устаревший), Java-аннотации (@Component, @Service, @Repository, @Controller + @ComponentScan), Java-конфигурацию (@Configuration + @Bean методы).

**В: Что такое Spring Bean? Жизненный цикл бина.**

О: Bean — объект, управляемый Spring IoC-контейнером. Жизненный цикл: создание экземпляра (instantiation); заполнение свойств (populate properties / dependency injection); вызов BeanNameAware.setBeanName() если реализует; вызов BeanFactoryAware.setBeanFactory() если реализует; вызов ApplicationContextAware.setApplicationContext() если реализует; вызов BeanPostProcessor.postProcessBeforeInitialization() — для всех зарегистрированных BPP; вызов @PostConstruct метода (или InitializingBean.afterPropertiesSet() или init-method); вызов BeanPostProcessor.postProcessAfterInitialization() — здесь создаются прокси для AOP; бин готов к использованию; при закрытии контекста: вызов @PreDestroy (или DisposableBean.destroy() или destroy-method).

BeanPostProcessor — мощный механизм. Вызывается для каждого бина. Позволяет модифицировать бин до и после инициализации. Используется фреймворком повсеместно: AutowiredAnnotationBeanPostProcessor обрабатывает @Autowired, CommonAnnotationBeanPostProcessor обрабатывает @PostConstruct / @PreDestroy.

**В: Scopes бинов в Spring.**

О: Singleton (по умолчанию) — один экземпляр на весь ApplicationContext. Все запросы возвращают один и тот же объект. Потокобезопасность — ответственность разработчика.

Prototype — новый экземпляр при каждом запросе из контейнера. Spring не управляет полным жизненным циклом: @PreDestroy не вызывается.

Request — один экземпляр на HTTP-запрос (только в web-контексте). Аннотация @RequestScope.

Session — один экземпляр на HTTP-сессию. Аннотация @SessionScope.

Application — один экземпляр на ServletContext (аналогично singleton, но в контексте сервлетов).

Websocket — один экземпляр на WebSocket-сессию.

Проблема inject'а Prototype в Singleton: если singleton-бин зависит от prototype-бина, prototype будет создан только один раз — при создании singleton'а. Решения: ObjectFactory<T> или Provider<T> (javax.inject) вместо прямой зависимости; Method Injection (@Lookup); ApplicationContext.getBean() (наименее элегантно).

**В: Что такое @Autowired? Как разрешаются конфликты?**

О: @Autowired — аннотация для автоматического внедрения зависимостей. Spring ищет в контейнере бин подходящего типа. Если найден один — внедряет. Если не найден — ошибка (если не @Autowired(required = false)). Если найдено несколько — нужно разрешить конфликт.

Способы разрешения: @Primary — на одном из бинов, делает его приоритетным; @Qualifier("name") — явное указание имени бина; по имени переменной — если имя параметра совпадает с именем бина; @Profile — бин активируется только для определённого профиля.

**В: Spring AOP — аспектно-ориентированное программирование.**

О: AOP позволяет выделить сквозную функциональность (cross-cutting concerns) — логирование, транзакции, безопасность, кэширование — в отдельные модули (аспекты), не смешивая с бизнес-логикой.

Ключевые понятия: Aspect — модуль с cross-cutting логикой (@Aspect); Join Point — точка в выполнении программы (вызов метода, выброс исключения); Pointcut — выражение, определяющее набор join points (@Pointcut("execution(* com.example.service.*.*(..))")); Advice — действие, выполняемое в join point: @Before (до), @After (после), @AfterReturning (после успешного возврата), @AfterThrowing (после исключения), @Around (оборачивает — самый мощный).

Реализация в Spring — через прокси. Два типа: JDK Dynamic Proxy — если бин реализует интерфейс (создаёт прокси-объект, реализующий тот же интерфейс); CGLIB Proxy — если бин не реализует интерфейс (создаёт подкласс через генерацию байт-кода). Spring Boot по умолчанию использует CGLIB. Ограничения: AOP работает только для public-методов; не работает при вызове метода внутри того же класса (self-invocation), потому что вызов идёт напрямую, минуя прокси.

### 2.2. Spring Boot

**В: Что такое Spring Boot и его преимущества?**

О: Spring Boot — надстройка над Spring Framework, облегчающая конфигурацию и запуск приложений. Ключевые преимущества: автоконфигурация (@EnableAutoConfiguration) — Spring Boot автоматически конфигурирует бины на основе classpath (если есть H2 — настроит DataSource, если есть Tomcat — запустит embedded-сервер); стартеры (spring-boot-starter-web, spring-boot-starter-data-jpa и т.д.) — готовые наборы зависимостей; встроенный сервер (Tomcat, Jetty, Undertow) — не нужен отдельный application server; Actuator — endpoints для мониторинга (/health, /metrics, /info, /env); профили — разные конфигурации для разных окружений (application-dev.yml, application-prod.yml); Spring Boot DevTools — hot reload при разработке.

**В: Как работает автоконфигурация?**

О: При запуске Spring Boot сканирует META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (или spring.factories для старых версий). Там перечислены классы автоконфигурации. Каждый класс помечен условными аннотациями: @ConditionalOnClass — если класс есть в classpath; @ConditionalOnMissingBean — если такого бина ещё нет (позволяет переопределить); @ConditionalOnProperty — если свойство установлено; @ConditionalOnBean — если указанный бин существует. Благодаря этому: если в classpath есть spring-webmvc + Tomcat — автоматически настроится DispatcherServlet и встроенный Tomcat; если есть DataSource в classpath и настроены spring.datasource.* — автоматически создастся DataSource; если вы явно определите свой бин DataSource — автоконфигурация отступит (@ConditionalOnMissingBean).

**В: Spring Boot Actuator — что это и зачем?**

О: Actuator предоставляет production-ready endpoints для мониторинга и управления приложением. /health — состояние приложения и его зависимостей (БД, Kafka, дисковое пространство); /metrics — метрики JVM, HTTP-запросов, кэша, соединений к БД; /info — информация о приложении; /env — переменные окружения и свойства; /loggers — динамическое изменение уровня логирования; /threaddump — дамп потоков; /heapdump — дамп кучи. Endpoints можно выставлять через HTTP или JMX. Важно ограничить доступ в production через Spring Security. Интегрируется с Prometheus, Grafana, Micrometer.

### 2.3. Spring MVC / Spring Web

**В: Как работает Spring MVC? DispatcherServlet.**

О: Spring MVC основан на паттерне Front Controller. DispatcherServlet — единая точка входа для всех HTTP-запросов. Цикл обработки запроса: запрос приходит в DispatcherServlet; HandlerMapping определяет, какой контроллер/метод обработает запрос (на основе URL, HTTP-метода, заголовков); HandlerAdapter вызывает соответствующий метод контроллера; контроллер обрабатывает запрос и возвращает ответ (ModelAndView для MVC или @ResponseBody для REST); ViewResolver разрешает имя представления в конкретный файл (для MVC); HttpMessageConverter сериализует/десериализует тело запроса/ответа (для REST — Jackson для JSON).

**В: Разница между @Controller и @RestController?**

О: @Controller — помечает класс как Spring MVC-контроллер. Методы по умолчанию возвращают имя View (строку, которую ViewResolver преобразует в страницу). Для возврата данных напрямую нужно добавлять @ResponseBody на каждый метод.

@RestController — комбинация @Controller + @ResponseBody. Все методы автоматически сериализуют возвращаемый объект в тело ответа (обычно JSON через Jackson). Идеально для REST API.

**В: Обработка исключений в Spring MVC.**

О: @ExceptionHandler — метод в контроллере, обрабатывающий конкретное исключение. @ControllerAdvice / @RestControllerAdvice — глобальный обработчик исключений для всех контроллеров. ResponseEntityExceptionHandler — базовый класс для обработки стандартных Spring MVC исключений. Рекомендуемый подход: создать @RestControllerAdvice с @ExceptionHandler для каждого типа исключений, возвращая стандартизированный DTO ошибки с кодом, сообщением и timestamp.

### 2.4. Spring Data JPA

**В: Что такое Spring Data JPA?**

О: Spring Data JPA — абстракция над JPA (Java Persistence API), минимизирующая boilerplate-код для работы с БД. Ключевые компоненты: Repository-интерфейсы — достаточно объявить интерфейс, наследующий JpaRepository<Entity, ID>, и Spring автоматически создаст реализацию с методами CRUD. Query Methods — методы, имя которых определяет запрос: findByNameAndAge(String name, int age), findByStatusOrderByCreatedAtDesc(Status status). @Query — кастомные JPQL или native SQL запросы: `@Query("SELECT u FROM User u WHERE u.email = :email")`. Specifications — программное построение запросов через Criteria API. Pagination — Pageable параметр + Page<T> возвращаемый тип.

**В: Что такое JPA и Hibernate? В чём разница?**

О: JPA (Java Persistence API) — спецификация (стандарт) для ORM в Java. Определяет аннотации (@Entity, @Table, @Column, @OneToMany и т.д.), EntityManager API, JPQL (Java Persistence Query Language). JPA сама по себе — только набор интерфейсов и аннотаций.

Hibernate — самая популярная реализация JPA. Предоставляет дополнительную функциональность: HQL (Hibernate Query Language — расширение JPQL), кэш второго уровня (L2 Cache), ленивая загрузка, batching, Envers (аудит), Multi-tenancy. EclipseLink — ещё одна реализация JPA.

**В: Проблема N+1 запросов и как её решить?**

О: N+1 — когда загрузка списка из N сущностей генерирует 1 запрос на список + N запросов на связанные сущности для каждого элемента. Например: `SELECT * FROM orders` (1 запрос), затем для каждого order: `SELECT * FROM order_items WHERE order_id = ?` (N запросов).

Решения: FETCH JOIN в JPQL: `SELECT o FROM Order o JOIN FETCH o.items` — загружает связанные данные одним запросом; @EntityGraph — декларативное указание, какие связи загрузить: `@EntityGraph(attributePaths = {"items"})` на методе репозитория; @BatchSize(size = N) на коллекции — Hibernate загружает связи пакетами, N SELECT'ов вместо N*M; DTO-проекции через @Query с конструктором — загружаем только нужные поля, избегая entity-графов. Fetch JOIN может привести к Cartesian Product при нескольких коллекциях — в таком случае лучше @BatchSize или несколько запросов.

**В: Что такое @Transactional?**

О: @Transactional — аннотация для декларативного управления транзакциями. Работает через AOP-прокси: Spring оборачивает метод, открывая транзакцию до вызова и коммитя (или откатывая) после.

Ключевые атрибуты: propagation — поведение при вложенных транзакциях: REQUIRED (по умолчанию, использует существующую или создаёт новую), REQUIRES_NEW (всегда создаёт новую, приостанавливая текущую), MANDATORY (требует существующую, иначе исключение), SUPPORTS, NOT_SUPPORTED, NEVER, NESTED. isolation — уровень изоляции: READ_UNCOMMITTED, READ_COMMITTED, REPEATABLE_READ, SERIALIZABLE. rollbackFor — какие исключения вызывают откат (по умолчанию: RuntimeException и Error; checked exceptions НЕ вызывают откат). readOnly — подсказка для оптимизации: Hibernate не делает dirty checking.

Важно: @Transactional работает только на public-методах; не работает при self-invocation (вызов из того же класса); класс должен быть Spring-бином; для REQUIRES_NEW — Spring создаёт отдельное соединение.

### 2.5. Spring Security (основы + JWT)

**В: Архитектура Spring Security.**

О: Основа — цепочка фильтров (SecurityFilterChain). Каждый HTTP-запрос проходит через набор фильтров до и после контроллера. Ключевые фильтры: SecurityContextPersistenceFilter — восстанавливает/сохраняет SecurityContext; UsernamePasswordAuthenticationFilter — обработка форм-логина; BasicAuthenticationFilter — HTTP Basic; ExceptionTranslationFilter — обработка исключений безопасности; FilterSecurityInterceptor / AuthorizationFilter — проверка прав доступа.

Основные компоненты: Authentication — объект, хранящий данные аутентификации (principal, credentials, authorities); SecurityContext — хранит текущий Authentication; SecurityContextHolder — потоко-безопасный контейнер для SecurityContext (по умолчанию ThreadLocal); AuthenticationManager — управляет процессом аутентификации; AuthenticationProvider — реализует конкретную стратегию аутентификации; UserDetailsService — загружает данные пользователя.

**В: Как работает JWT-аутентификация?**

О: JWT (JSON Web Token) — стандарт (RFC 7519) для передачи заявлений (claims) между сторонами в виде самодостаточного токена. Структура: три части, разделённые точками: Header (алгоритм и тип токена), Payload (claims — данные: sub, iat, exp, custom), Signature (подпись для верификации целостности).

Процесс: клиент отправляет login/password; сервер проверяет credentials; при успехе — генерирует JWT с payload (userId, roles, expiration) и подписывает secret-ключом (HMAC) или приватным ключом (RSA/ECDSA); клиент сохраняет токен и отправляет в заголовке Authorization: Bearer <token>; на каждый запрос: фильтр извлекает токен, проверяет подпись и expiration, извлекает данные пользователя, создаёт Authentication и помещает в SecurityContext.

Реализация в Spring: создать JwtTokenProvider (генерация, валидация, парсинг токена); создать JwtAuthenticationFilter (OncePerRequestFilter — извлекает токен из заголовка, валидирует, устанавливает Authentication); зарегистрировать фильтр в SecurityFilterChain до UsernamePasswordAuthenticationFilter.

Refresh Token: access token живёт коротко (15-30 минут); refresh token — дольше (дни/недели), хранится в HttpOnly cookie или в БД; при истечении access token — клиент запрашивает новый, предъявляя refresh token.

## ЧАСТЬ 3. APACHE KAFKA

### 3.1. Основы Kafka

**В: Что такое Apache Kafka?**

О: Kafka — распределённая потоковая платформа для построения data pipelines и event-driven приложений. Основана на модели publish-subscribe. Ключевые характеристики: высокая пропускная способность (миллионы сообщений в секунду), масштабируемость (горизонтальная через добавление брокеров), отказоустойчивость (репликация данных между брокерами), хранение данных (сообщения сохраняются на диск, доступны повторно), гарантии порядка (внутри одной партиции).

**В: Основные компоненты Kafka.**

О: Broker — сервер Kafka, хранящий данные. Кластер состоит из нескольких брокеров. Topic — именованный канал для потока сообщений. Логическая категория. Partition — разделение топика на упорядоченные, неизменяемые последовательности сообщений. Каждая партиция — это коммит-лог. Сообщениям в партиции назначается последовательный offset. Партиции распределяются по брокерам — это основа масштабируемости. Producer — приложение, отправляющее сообщения в топик. Consumer — приложение, читающее сообщения из топика. Consumer Group — группа потребителей, совместно потребляющих топик: каждая партиция назначается ровно одному потребителю в группе. Это обеспечивает параллельную обработку и отсутствие дублирования. Zookeeper / KRaft — координация кластера (выбор лидера, управление метаданными). С Kafka 3.3+ Zookeeper заменяется на KRaft (Kafka Raft).

**В: Что такое Offset? Как управляется?**

О: Offset — уникальный последовательный идентификатор сообщения внутри партиции. Начинается с 0 и монотонно растёт. Consumer отслеживает свой offset — позицию до которой он прочитал. Offsets хранятся в внутреннем топике __consumer_offsets.

Стратегии коммита: auto-commit (enable.auto.commit=true) — Kafka автоматически коммитит offset через интервал auto.commit.interval.ms; рискованно: при падении между коммитами — повторная обработка; при коммите до обработки — потеря данных. Manual commit: commitSync() — синхронный коммит, блокирует до подтверждения; commitAsync() — асинхронный, быстрее, но при ошибке нет повтора. Рекомендуемая практика — ручной коммит после успешной обработки.

auto.offset.reset: earliest — читать с начала (если offset утерян); latest — читать только новые сообщения; none — ошибка, если offset не найден.

**В: Как обеспечивается отказоустойчивость?**

О: Replication — каждая партиция реплицируется на несколько брокеров (replication factor). Одна реплика — лидер (обрабатывает чтение и запись), остальные — фоллоуеры (синхронизируют данные с лидером). ISR (In-Sync Replicas) — набор реплик, синхронизированных с лидером. Если лидер падает — один из ISR становится новым лидером. min.insync.replicas — минимальное число ISR для подтверждения записи.

acks (acknowledgement): acks=0 — producer не ждёт подтверждения (возможна потеря); acks=1 — ждёт подтверждения от лидера (потеря при падении лидера до репликации); acks=all (-1) — ждёт подтверждения от всех ISR (самая надёжная гарантия); в сочетании с min.insync.replicas=2 и replication.factor=3 — оптимальная конфигурация для production.

**В: Гарантии доставки сообщений.**

О: At most once — сообщение может быть потеряно, но не продублировано. (auto-commit, acks=0). At least once — сообщение не потеряется, но может быть продублировано. (manual commit после обработки, acks=all, retry). Exactly once — сообщение обрабатывается ровно один раз. Реализуется через: идемпотентный producer (enable.idempotence=true — Kafka дедуплицирует по ProducerID + SequenceNumber); транзакции (transactional.id — атомарная запись в несколько партиций/топиков + коммит offset в одной транзакции: read-process-write pattern).

**В: Как работает партиционирование?**

О: Producer определяет партицию для сообщения: если указан ключ — по хэшу ключа (murmur2) mod количество_партиций; гарантирует, что сообщения с одним ключом попадут в одну партицию (порядок внутри ключа). Если ключ null — Round Robin (до Kafka 2.4) или Sticky Partitioner (с Kafka 2.4 — накапливает batch для одной партиции, затем переключается — лучше batching). Можно реализовать свой Partitioner.

Количество партиций: определяет максимальный параллелизм потребителей (consumer'ов в группе не может быть больше, чем партиций); увеличение партиций — необратимо и не перераспределяет существующие данные; общая рекомендация: начать с количества партиций = max(ожидаемый throughput / throughput одного consumer, количество брокеров).

### 3.2. Spring Kafka

**В: Как интегрировать Kafka со Spring?**

О: Зависимость: spring-kafka (spring-boot-starter для Spring Boot). Producer: KafkaTemplate — основной класс для отправки. Конфигурация: ProducerConfig (bootstrap.servers, key.serializer, value.serializer). Метод send() возвращает CompletableFuture для асинхронной обработки результата. Сериализация: StringSerializer, JsonSerializer, AvroSerializer (с Schema Registry).

Consumer: @KafkaListener — аннотация на методе, подписывающая на топик. Конфигурация: ConsumerConfig (bootstrap.servers, group.id, key.deserializer, value.deserializer, auto.offset.reset). ConcurrentKafkaListenerContainerFactory — настройка параллелизма (concurrency), ack-mode, error handler.

Error handling: DefaultErrorHandler — настраиваемый retry (BackOff) + отправка в DLT (Dead Letter Topic) после исчерпания попыток. RetryableTopic (@RetryableTopic) — декларативный retry с отдельными retry-топиками и экспоненциальным backoff.

## ЧАСТЬ 4. БАЗЫ ДАННЫХ (PostgreSQL)

---

### 4.1. SQL и реляционные концепции

**В: Типы JOIN'ов.**

О: INNER JOIN — возвращает только строки, имеющие совпадения в обеих таблицах. LEFT (OUTER) JOIN — все строки из левой таблицы + совпадения из правой; если совпадения нет — NULL для колонок правой таблицы. RIGHT (OUTER) JOIN — все строки из правой таблицы + совпадения из левой. FULL (OUTER) JOIN — все строки из обеих таблиц; NULL где нет совпадений. CROSS JOIN — декартово произведение (каждая строка с каждой). SELF JOIN — таблица соединяется сама с собой (для иерархических данных, поиск дубликатов). NATURAL JOIN — автоматический JOIN по столбцам с одинаковыми именами (опасен — неявное поведение).

**В: Индексы — типы, когда использовать, когда нет.**

О: Индекс — структура данных, ускоряющая поиск. В PostgreSQL: B-tree (по умолчанию) — для операций сравнения (=, <, >, BETWEEN, ORDER BY); подходит для большинства случаев. Hash — только для точного равенства (=); в PostgreSQL до 10 был ненадёжен, сейчас улучшен. GiST (Generalized Search Tree) — для геопространственных данных (PostGIS), полнотекстового поиска, диапазонных типов. GIN (Generalized Inverted Index) — для массивов, JSONB, полнотекстового поиска (лучше для частых поисков, медленнее обновление). BRIN (Block Range Index) — для очень больших таблиц с естественным порядком данных (timestamp, ID); компактный.

Составной индекс: учитывает порядок колонок (leftmost prefix rule). INDEX(a, b, c) эффективен для запросов по (a), (a, b), (a, b, c), но НЕ для (b), (c), (b, c).

Когда НЕ использовать: маленькие таблицы (full scan быстрее); колонки с низкой селективностью (boolean, status с 2-3 значениями); таблицы с частыми INSERT/UPDATE/DELETE (индекс замедляет запись); если запрос затрагивает большой процент строк (>10-20%).

Покрывающий индекс (Covering Index): INCLUDE позволяет добавить в индекс колонки, по которым не идёт поиск, но которые нужны в SELECT — Index Only Scan, без обращения к таблице.

**В: Нормализация базы данных.**

О: 1NF: каждая ячейка содержит атомарное значение; нет повторяющихся групп. 2NF: 1NF + каждый неключевой атрибут полностью зависит от первичного ключа (не от части составного ключа). 3NF: 2NF + нет транзитивных зависимостей (неключевой атрибут не зависит от другого неключевого). BCNF (Бойса-Кодда): каждая нетривиальная функциональная зависимость определяется суперключом.

Денормализация — осознанное отступление от нормальных форм для ускорения чтения (дублирование данных, предварительно вычисленные поля). Применяется в отчётных системах, data warehouses, когда чтение критичнее записи.

**В: Транзакции. ACID. Уровни изоляции.**

О: ACID: Atomicity — транзакция выполняется целиком или не выполняется вообще; Consistency — БД переходит из одного согласованного состояния в другое; Isolation — параллельные транзакции не влияют друг на друга; Durability — результат зафиксированной транзакции сохраняется даже при сбое.

Проблемы параллельного доступа: Dirty Read — чтение незафиксированных данных другой транзакции; Non-repeatable Read — повторное чтение одной строки даёт разные результаты; Phantom Read — повторный запрос возвращает строки, которых не было.

Уровни изоляции (от слабого к сильному): READ UNCOMMITTED — допускает dirty reads; READ COMMITTED (дефолт в PostgreSQL) — видит только зафиксированные данные; REPEATABLE READ — гарантирует одинаковый результат повторного чтения строки; SERIALIZABLE — полная изоляция, как если бы транзакции выполнялись последовательно.

PostgreSQL использует MVCC (Multi-Version Concurrency Control): каждая транзакция видит «снимок» данных на момент начала; писатели не блокируют читателей; при конфликтах — откат с предложением повторить.

**В: EXPLAIN / EXPLAIN ANALYZE — как читать план запроса?**

О: EXPLAIN показывает план выполнения запроса без его выполнения. EXPLAIN ANALYZE — выполняет и показывает реальное время.

Ключевые операции: Seq Scan — последовательный просмотр всей таблицы (может быть нормально для маленьких таблиц); Index Scan — поиск по индексу + обращение к таблице; Index Only Scan — данные берутся только из индекса (покрывающий индекс); Bitmap Index Scan + Bitmap Heap Scan — индексный поиск с формированием битовой карты страниц; Nested Loop — для каждой строки одной таблицы — поиск в другой; Hash Join — построение хэш-таблицы из меньшей таблицы, поиск для каждой строки большей; Merge Join — слияние двух отсортированных наборов.

На что смотреть: cost (startup..total) — оценочная стоимость; rows — оценочное число строк; actual time и actual rows — реальные значения (только с ANALYZE); loops — сколько раз операция повторяется; buffers — количество прочитанных страниц (shared hit — из кэша, shared read — с диска).

### 4.2. Особенности PostgreSQL

**В: Специфические возможности PostgreSQL.**

О: JSONB — бинарное хранение JSON с индексацией (GIN-индекс), операторами (@>, ->, ->>, ?) и функциями; мощная альтернатива NoSQL. Window Functions — аналитические функции: ROW_NUMBER(), RANK(), DENSE_RANK(), LAG(), LEAD(), SUM() OVER(PARTITION BY ... ORDER BY ...) — выполняют вычисления над набором строк, связанных с текущей, без группировки. CTE (Common Table Expressions) — WITH-запросы для декомпозиции сложных запросов; рекурсивные CTE для иерархических данных (WITH RECURSIVE). Partitioning — разбиение большой таблицы на секции (по диапазону, списку, хэшу); ускоряет запросы с фильтром по ключу партиционирования, упрощает удаление старых данных. LISTEN/NOTIFY — встроенный механизм pub/sub для уведомлений между процессами. Full Text Search — встроенный полнотекстовый поиск с tsvector, tsquery, GIN-индексом. Materialized Views — кэшированные результаты запроса, обновляемые по REFRESH MATERIALIZED VIEW.

## ЧАСТЬ 5. UNIT-ТЕСТИРОВАНИЕ

---

**В: Что такое unit-тест? Принципы написания.**

О: Unit-тест — тест, проверяющий наименьшую единицу кода (метод, класс) в изоляции от внешних зависимостей. Принципы FIRST: Fast (быстрые), Independent (не зависят друг от друга), Repeatable (дают одинаковый результат), Self-Validating (автоматически проверяют результат), Timely (пишутся своевременно, желательно до кода — TDD).

Паттерн AAA: Arrange (подготовка данных и зависимостей); Act (выполнение тестируемого действия); Assert (проверка результата).

**В: JUnit 5 — основные аннотации и возможности.**

О: @Test — помечает метод как тест. @BeforeEach / @AfterEach — выполняется до/после каждого теста (замена @Before/@After из JUnit 4). @BeforeAll / @AfterAll — выполняется один раз до/после всех тестов (static-методы). @DisplayName("Human-readable name") — читаемое имя теста. @Disabled — пропустить тест. @ParameterizedTest — параметризированный тест с @ValueSource, @CsvSource, @MethodSource, @EnumSource — запуск теста с разными входными данными. @Nested — вложенные тестовые классы для логической группировки. @Tag — метки для фильтрации тестов. @Timeout — ограничение времени выполнения.

Assertions: assertEquals, assertNotEquals, assertTrue, assertFalse, assertNull, assertNotNull, assertThrows(ExceptionClass, executable), assertDoesNotThrow(), assertAll(executable...) — группирует проверки, показывает все ошибки. assertTimeout — проверка выполнения за отведённое время.

**В: Mockito — мокирование зависимостей.**

О: Mock — объект-заглушка, имитирующий поведение зависимости. Создание: @Mock аннотация или Mockito.mock(Class). @InjectMocks — создаёт экземпляр тестируемого класса и внедряет моки.

Stubbing (определение поведения): when(mock.method(args)).thenReturn(value) — вернуть значение; when(...).thenThrow(exception) — бросить исключение; when(...).thenAnswer(invocation -> ...) — динамическое вычисление.

Verification (проверка вызовов): verify(mock).method(args) — был ли вызван; verify(mock, times(2)).method() — сколько раз; verify(mock, never()).method() — не вызывался; verify(mock, atLeastOnce()).method().

Argument matchers: any(), anyString(), anyLong(), eq(value), argThat(predicate). ArgumentCaptor — захват аргумента для детальной проверки.

Spy — частичный мок: реальный объект, у которого можно переопределить отдельные методы. @Spy или Mockito.spy(). Отличие от mock: spy вызывает реальные методы по умолчанию.

**В: Тестирование в Spring Boot.**

О: @SpringBootTest — поднимает полный Spring-контекст. Тяжёлый, для интеграционных тестов. @WebMvcTest(Controller.class) — поднимает только веб-слой. MockMvc для тестирования HTTP-запросов без реального сервера: mockMvc.perform(get("/api/users")).andExpect(status().isOk()).andExpect(jsonPath("$.name").value("John")). @DataJpaTest — поднимает только JPA-слой с встроенной БД (H2). Настраивает EntityManager, Repositories, транзакционность (откат после каждого теста). @MockBean — создаёт мок Spring-бина и подставляет его в контекст вместо реального.

Testcontainers — библиотека для запуска реальных зависимостей (PostgreSQL, Kafka, Redis) в Docker-контейнерах во время тестов. Идеально для интеграционных тестов, максимально близких к production.

## ЧАСТЬ 6. XML

---

**В: Парсинг XML в Java — DOM, SAX, StAX.**

О: DOM (Document Object Model) — загружает весь XML в память как дерево объектов. Плюсы: удобная навигация, модификация документа. Минусы: потребление памяти пропорционально размеру файла; не подходит для больших файлов. Используется: javax.xml.parsers.DocumentBuilderFactory.

SAX (Simple API for XML) — событийный парсер. Читает XML последовательно, вызывая callback'и (startElement, endElement, characters). Плюсы: минимальное потребление памяти, быстрый. Минусы: только чтение, нет навигации назад, сложнее программирование. Используется: javax.xml.parsers.SAXParserFactory.

StAX (Streaming API for XML) — pull-парсинг: приложение запрашивает следующее событие (в отличие от push-парсинга SAX). Два варианта: cursor API (XMLStreamReader) и iterator API (XMLEventReader). Баланс между DOM и SAX. Используется: javax.xml.stream.XMLInputFactory.

JAXB (Java Architecture for XML Binding) — маршаллинг/демаршаллинг: автоматическое преобразование между XML и Java-объектами через аннотации (@XmlRootElement, @XmlElement, @XmlAttribute). Удалён из JDK 11+, нужна отдельная зависимость (jakarta.xml.bind).

**В: Что такое XSD и XSLT?**

О: XSD (XML Schema Definition) — язык описания структуры XML-документа. Определяет допустимые элементы, атрибуты, типы данных, ограничения, порядок элементов, обязательность. Используется для валидации: является ли XML-документ корректным относительно схемы. В Java — javax.xml.validation.SchemaFactory для валидации XML по XSD.

XSLT (Extensible Stylesheet Language Transformations) — язык преобразования XML-документов. Принимает на вход XML и шаблон XSLT, производит выходной документ (XML, HTML, текст). Шаблон описывает правила трансформации через match-шаблоны и XPath-выражения. В Java — javax.xml.transform.TransformerFactory. Применение: преобразование XML в HTML для отображения, конвертация между форматами XML, генерация отчётов.

## ЧАСТЬ 7. DOCKER И KUBERNETES

---

### 7.1. Docker

**В: Что такое Docker? Основные концепции.**

О: Docker — платформа контейнеризации, позволяющая упаковать приложение со всеми зависимостями в стандартизированный контейнер. Image — неизменяемый шаблон для создания контейнеров. Состоит из слоёв (layers), каждая инструкция Dockerfile создаёт новый слой. Container — запущенный экземпляр image. Изолирован от хост-системы (namespaces, cgroups). Запись происходит в тонкий read-write слой поверх image. Dockerfile — инструкция для сборки image. Registry — хранилище image'ей (Docker Hub, Gitlab Container Registry, AWS ECR).

**В: Ключевые инструкции Dockerfile.**

О: FROM — базовый image. COPY / ADD — копирование файлов (COPY предпочтительнее; ADD умеет распаковывать архивы и загружать по URL). RUN — выполнение команды при сборке (установка зависимостей). CMD — команда по умолчанию при запуске контейнера. ENTRYPOINT — основная команда (CMD дополняет аргументами). EXPOSE — документирование порта (не открывает порт). ENV — переменные окружения. WORKDIR — рабочая директория. ARG — аргументы сборки. VOLUME — точка монтирования.

Multi-stage build — несколько FROM в одном Dockerfile: на первом этапе — сборка (с JDK, Maven), на втором — только runtime (JRE). Результат — значительно меньший финальный image.

**В: Docker Compose — зачем и как?**

О: Docker Compose — инструмент для определения и запуска multi-container приложений через YAML-файл (docker-compose.yml). Описываете сервисы (services), сети (networks), тома (volumes). Одна команда `docker-compose up` запускает всё окружение. Идеально для local development: приложение + PostgreSQL + Kafka + Redis в одном файле.

### 7.2. Kubernetes

**В: Что такое Kubernetes? Основные компоненты.**

О: Kubernetes (K8s) — платформа оркестрации контейнеров. Управляет развёртыванием, масштабированием, самовосстановлением контейнеризированных приложений.

Control Plane: kube-apiserver (API для взаимодействия с кластером), etcd (распределённое хранилище ключ-значение для состояния кластера), kube-scheduler (распределяет поды по нодам), kube-controller-manager (контроллеры: ReplicaSet controller, Deployment controller, Node controller и др.).

Worker Nodes: kubelet (агент на каждой ноде, управляет подами), kube-proxy (сетевой прокси, правила маршрутизации), Container Runtime (Docker, containerd, CRI-O).

**В: Основные ресурсы Kubernetes.**

О: Pod — минимальная единица развёртывания; один или несколько контейнеров, разделяющих сеть и хранилище. Deployment — управляет ReplicaSet, обеспечивает декларативное обновление (rolling update, rollback), нужное количество реплик. Service — абстракция для доступа к набору подов: ClusterIP (внутренний IP), NodePort (порт на каждой ноде), LoadBalancer (внешний балансировщик). ConfigMap — конфигурация (не секретная) в виде ключ-значение; монтируется как файлы или переменные окружения. Secret — конфигурация для чувствительных данных (Base64-encoded; в production — шифрование через KMS). Ingress — управление внешним HTTP/HTTPS-доступом (маршрутизация по URL/host, TLS-терминация). Namespace — логическое разделение ресурсов кластера. PersistentVolume (PV) / PersistentVolumeClaim (PVC) — хранилище данных.

**В: Rolling Update и стратегии развёртывания.**

О: Rolling Update (дефолт Deployment) — постепенная замена старых подов новыми. Параметры: maxSurge (сколько новых подов сверх desired count), maxUnavailable (сколько подов могут быть недоступны). Recreate — удалить все старые, создать новые (downtime). Blue-Green — два идентичных окружения; переключение трафика целиком. Canary — новая версия на маленький процент трафика; мониторинг; постепенное увеличение. K8s нативно поддерживает Rolling Update и Recreate; Blue-Green и Canary реализуются через Istio, Argo Rollouts, Flagger.

## ЧАСТЬ 8. GIT

---

**В: Основные концепции и команды Git.**

О: Git — распределённая система контроля версий. Каждый разработчик имеет полную копию репозитория. Основные области: Working Directory (рабочая копия), Staging Area / Index (подготовленные к коммиту изменения), Local Repository (.git), Remote Repository (сервер — GitLab, GitHub).

Ключевые команды: git clone — клонирование удалённого репозитория; git add — добавление в staging; git commit — фиксация изменений; git push — отправка на remote; git pull — получение + merge (git fetch + git merge); git fetch — получение без merge; git status — состояние рабочей директории; git log — история коммитов; git diff — различия.

Ветвление: git branch feature — создать ветку; git checkout feature / git switch feature — переключиться; git merge feature — слить в текущую ветку; git rebase main — перебазировать текущую ветку на main (переписывает историю — чистая линейная история, но опасно для shared-веток).

**В: Merge vs Rebase. Когда что использовать?**

О: Merge — создаёт merge-коммит, сохраняя полную историю обеих веток. Плюсы: безопасно (не переписывает историю), понятно, когда произошло слияние. Минусы: «грязная» история с merge-коммитами.

Rebase — берёт коммиты текущей ветки и «пересаживает» их на вершину целевой ветки. Плюсы: чистая линейная история. Минусы: переписывает хэши коммитов — никогда не делать rebase публичных (shared) веток. Правило: rebase для своих локальных веток перед merge в main; merge для объединения feature-веток в main.

Interactive rebase (git rebase -i): squash — объединить несколько коммитов; reword — изменить сообщение; drop — удалить коммит; fixup — объединить без сообщения.

**В: Git Flow и стратегии ветвления.**

О: Git Flow: main (production-ready), develop (интеграционная ветка), feature/* (новая функциональность, от develop), release/* (подготовка релиза, от develop), hotfix/* (экстренные исправления, от main). Подходит для проектов с выраженными релизами.

GitHub Flow (более простой): main + feature-ветки + Pull/Merge Requests. Подходит для continuous delivery. Trunk-Based Development — все работают в main/trunk, короткоживущие feature-ветки, feature flags.

## ЧАСТЬ 9. CI/CD

---

**В: Что такое CI/CD?**

О: CI (Continuous Integration) — практика частого слияния кода в общую ветку с автоматической сборкой и тестированием. Цели: раннее обнаружение ошибок, уменьшение конфликтов при интеграции, постоянно работающая кодовая база.

CD — два значения: Continuous Delivery — автоматическая доставка артефакта в staging/pre-production, деплой в production — по кнопке; Continuous Deployment — полная автоматизация, каждый прошедший тесты коммит автоматически попадает в production.

Типичный CI/CD pipeline: commit → build (компиляция) → unit tests → integration tests → static analysis (SonarQube) → build Docker image → push to registry → deploy to staging → acceptance tests → deploy to production (manual approval для CD, автоматически для Continuous Deployment).

**В: GitLab CI/CD — как настроить?**

О: Конфигурация через .gitlab-ci.yml в корне репозитория. Основные концепции: stages — этапы (build, test, deploy); jobs — задачи внутри этапов (запускаются параллельно в одном stage); runners — серверы, выполняющие jobs (shared или dedicated); artifacts — файлы, передаваемые между jobs; cache — кэш зависимостей между пайплайнами; variables — переменные (в файле или в настройках проекта); environment — целевое окружение (staging, production); rules / only / except — условия запуска job.

## ЧАСТЬ 10. KEY-VALUE DATABASES (Redis)

---

**В: Что такое Redis? Основные структуры данных.**

О: Redis — in-memory key-value хранилище. Данные хранятся в оперативной памяти, что обеспечивает микросекундные задержки. Может сохранять данные на диск (persistence): RDB (snapshots) и AOF (Append Only File — журнал операций).

Структуры данных: String — базовый тип, до 512 МБ; используется для кэширования, счётчиков (INCR/DECR), сессий. List — упорядоченный список строк (двусвязный список); LPUSH, RPUSH, LPOP, RPOP, LRANGE; подходит для очередей, логов. Set — неупорядоченная коллекция уникальных строк; SADD, SREM, SMEMBERS, SINTER (пересечение), SUNION (объединение). Sorted Set (ZSet) — Set с весом (score) для каждого элемента; ZADD, ZRANK, ZRANGE; подходит для рейтингов, лидербордов. Hash — аналог HashMap; HSET, HGET, HGETALL; подходит для хранения объектов (user:1 → {name, email, age}). Stream — журнал событий (аналог Kafka-топика); XADD, XREAD, XREADGROUP.

**В: Паттерны использования Redis.**

О: Кэширование: Cache-Aside — приложение проверяет кэш, при промахе читает из БД и кладёт в кэш; Write-Through — запись и в кэш, и в БД; Write-Behind — запись в кэш, асинхронная запись в БД. TTL (Time To Live) — автоматическое удаление ключей по истечении времени. Eviction policies: noeviction, allkeys-lru, volatile-lru, allkeys-random, volatile-ttl и др.

Распределённые блокировки: SETNX (SET if Not eXists) + TTL для реализации distributed lock. Redlock — алгоритм от автора Redis для надёжных блокировок в кластере. Библиотека Redisson (Java) — удобная абстракция над Redis: RLock, RMap, RQueue и др.

Pub/Sub: SUBSCRIBE/PUBLISH — встроенный механизм pub/sub. Не хранит сообщения (fire-and-forget). Для надёжной доставки — Redis Streams.

Spring Data Redis: RedisTemplate — основной класс для работы; StringRedisTemplate — специализация для String. @Cacheable, @CacheEvict, @CachePut — декларативное кэширование через Spring Cache abstraction с Redis как backend.

## ЧАСТЬ 11. LINUX

---

**В: Основные команды для Java-разработчика.**

О: Навигация и файлы: ls, cd, pwd, mkdir, rm, cp, mv, find, locate. Просмотр содержимого: cat, less, more, head, tail, tail -f (следить за логом в реальном времени). Текст: grep (поиск по шаблону; grep -r "Exception" logs/), sed (потоковый редактор), awk (обработка текста по колонкам). Процессы: ps aux (все процессы), top/htop (мониторинг), kill/kill -9 (завершение), nohup (запуск в фоне), & (фоновый запуск). Сеть: curl (HTTP-запросы), wget (скачивание), netstat/ss (порты), ping, traceroute, nslookup/dig. Права: chmod (изменение прав), chown (владелец), sudo. Диск: df -h (свободное место), du -sh (размер директории). Работа с Java: jps (процессы JVM), jstack (thread dump), jmap (heap dump), jstat (статистика GC), jconsole/jvisualvm (мониторинг). Системные журналы: journalctl, /var/log/. Pipe и перенаправление: | (передача вывода), > (запись), >> (дополнение), 2>&1 (stderr в stdout).

## ЧАСТЬ 12. QUARKUS

---

**В: Что такое Quarkus? Отличия от Spring Boot.**

О: Quarkus — Java-фреймворк, оптимизированный для cloud-native и контейнерных окружений. Ключевые особенности: GraalVM Native Image — компиляция в нативный бинарник (время запуска ~десятки миллисекунд вместо секунд, минимальное потребление памяти); Build-Time Processing — максимум работы переносится на этап сборки (классы не сканируются при запуске, инъекция зависимостей разрешается при компиляции); Dev Mode — hot reload с непрерывным тестированием; MicroProfile-совместимость (CDI для DI, JAX-RS для REST, MicroProfile Config, Health, Metrics); поддержка реактивного программирования (Mutiny).

Сравнение с Spring Boot: Quarkus значительно быстрее запускается и потребляет меньше памяти, что критично для serverless и Kubernetes; Spring Boot имеет более зрелую экосистему, большее community, больше интеграций; Quarkus поддерживает Spring API через расширения (spring-web, spring-di), облегчая миграцию; выбор зависит от приоритетов: для микросервисов в Kubernetes с автоскейлингом Quarkus может быть предпочтительнее.

## ЧАСТЬ 13. ПАТТЕРНЫ ПРОЕКТИРОВАНИЯ

---

**В: Назовите основные паттерны и их применение.**

О: Creational (порождающие): Singleton — единственный экземпляр класса (Spring beans scope singleton); Factory Method — делегирование создания подклассам; Abstract Factory — семейства связанных объектов; Builder — поэтапное конструирование сложных объектов (Lombok @Builder, StringBuilder); Prototype — клонирование объектов.

Structural (структурные): Adapter — приведение интерфейса к ожидаемому (InputStreamReader); Decorator — динамическое добавление функциональности (BufferedInputStream обёрнутый вокруг FileInputStream); Proxy — подстановка заместителя (Spring AOP прокси, lazy loading в Hibernate); Facade — упрощённый интерфейс к подсистеме; Composite — древовидные структуры.

Behavioral (поведенческие): Strategy — семейство алгоритмов, выбираемых в runtime (Comparator); Observer — pub/sub, уведомление подписчиков об изменениях (ApplicationEvent в Spring); Template Method — скелет алгоритма в базовом классе (JdbcTemplate); Chain of Responsibility — цепочка обработчиков (SecurityFilterChain); Iterator — последовательный обход коллекции.

## ЧАСТЬ 14. СИСТЕМНЫЕ И АРХИТЕКТУРНЫЕ ВОПРОСЫ

---

**В: Монолит vs Микросервисы.**

О: Монолит — всё приложение в одном процессе/деплое. Плюсы: простота разработки и отладки, простые транзакции, простой деплой. Минусы: сложность масштабирования отдельных компонентов, длинные циклы деплоя, технологический lock-in, «big ball of mud» со временем.

Микросервисы — приложение разделено на маленькие независимые сервисы, каждый отвечает за одну бизнес-функцию. Плюсы: независимые деплои и масштабирование, технологическая гибкость, resilience (падение одного сервиса не роняет всё). Минусы: сложность распределённых систем (сетевые ошибки, eventual consistency, distributed transactions), operational overhead (мониторинг, логирование, трассировка), сложнее отладка.

**В: REST API — best practices.**

О: Ресурсы — существительные, не глаголы: /users, не /getUsers. HTTP-методы: GET (чтение), POST (создание), PUT (полное обновление), PATCH (частичное обновление), DELETE (удаление). Статус-коды: 200 OK, 201 Created, 204 No Content, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 500 Internal Server Error. Версионирование: /api/v1/users. Пагинация: ?page=0&size=20. Фильтрация: ?status=active&sort=createdAt,desc. HATEOAS — ссылки в ответе для навигации.

**В: Что такое идемпотентность?**

О: Операция идемпотентна, если её многократное выполнение даёт тот же результат, что и однократное. GET — идемпотентен (чтение не меняет состояние). PUT — идемпотентен (повторное обновление на те же данные — тот же результат). DELETE — идемпотентен (удаление уже удалённого — не ошибка или 404). POST — НЕ идемпотентен (создание нового ресурса при каждом вызове). Для обеспечения идемпотентности POST: использовать Idempotency-Key в заголовке; проверять дубликаты по бизнес-ключу. Критично важно для распределённых систем с retry-логикой.
